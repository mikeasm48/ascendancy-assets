# 05 — Дизайны строений и маппинги устройств в бандле

Бандл раздаёт не только модели, но и **базовый маппинг** «технология →
что показывать». Игра больше не знает ни одного захардкоженного имени
модели: чем выглядит строение или устройство, решают эти файлы, а если
для технологии ничего не найдено — подставляется заглушка семейства из
`common/science_tree_stubs/`.

## Две папки бандла

```
common/building-designs/{core,humans,shuffie}.json
common/device-mappings/{core,humans,shuffie}.json
```

Имя файла — id источника (`core`, `humans`, `shuffie`); раса Shuffie в
ассетах лежит в `bionics/`, но файл называется по расе, не по папке.

## Порядок поиска в игре

Для каждой расы движок идёт по цепочке и берёт первое найденное:

1. `~/.ascendancy/building-designs/<раса>.json` — пользовательский файл,
   сохранённый редактором;
2. `~/.ascendancy/assets/common/building-designs/<раса>.json` — этот
   бандл;
3. то же самое для источника `core`;
4. автомаппинг по glTF-`extras` конструкторов (см. ниже);
5. заглушка семейства из `common/science_tree_stubs/`.

Для устройств цепочка та же с `device-mappings`.

**Пользовательские файлы лежат вне `assets/`** — намеренно: распаковка
нового релиза чистит кэш ассетов целиком, и авторские правки внутри
`assets/` не пережили бы обновление. Поэтому пользовательский слой
живёт в `~/.ascendancy/{building-designs,device-mappings}/`, а бандл
раздаёт только базу и никогда её не перетирает.

## Автомаппинг: почему файлы можно не раздавать

Если для источника нет ни одного файла, игра выводит маппинг сама из
glTF-`extras` конструкторов. Для строений берутся узлы с
`kind` = `building`/`orbital`, чей `building_id` совпадает с
технологией; пропсы и варианты пропускаются. Для устройств матчинг
семантический, потому что в наборах два диалекта extras: новые киты
кладут в `device_id` id каталога (`ENGINE_1`) — совпадение прямое, а
core-набор называет узлы по артефакту (`Engine_TonklinMotor`), но его
`display_name` («Tonklin Motor») совпадает с именем устройства в
каталоге.

Отсюда практическое следствие: **корректные `extras` важнее, чем сами
json-файлы**. Файлы в бандле — это зафиксированный, вручную выверенный
слепок; автомаппинг — страховка для нового кита, который ещё не
размечен.

## Схема файлов

`building-designs/<источник>.json` — размещения по технологиям; одна
технология может собираться из нескольких конструкторов:

```json
{
  "sourceId": "humans",
  "byTech": {
    "FACTORY": {
      "techId": "FACTORY",
      "placements": [
        {
          "constructorFile": "building_constructor_industrial.glb",
          "elementId": "001_industrial_FACTORY",
          "partName": null,
          "offset": { "dx": 0.0, "dy": 0.0, "dz": 0.0,
                      "rx": 0.0, "ry": 0.0, "rz": 0.0,
                      "mirrorX": false, "mirrorY": false, "mirrorZ": false }
        }
      ]
    }
  }
}
```

`partName` = `null` ставит группу целиком; непустой — один меш-узел
внутри группы. `constructorFile` указывает на файл в
`races/<папка>/buildings/`.

`device-mappings/<источник>.json` — по одной модели на устройство:

```json
{
  "sourceId": "core",
  "bindings": {
    "ENGINE_1": {
      "constructorFile": "device_constructor.glb",
      "modelNode": "Engine_TonklinMotor"
    }
  }
}
```

## Текущее покрытие

| источник | строения / орбитали | устройства |
| --- | --- | --- |
| core    | 29 | 36 |
| humans  | 29 | 36 |
| shuffie | 29 | 36 |

29 = 14 наземных строений + 15 орбитальных конструкций (все тиры доков,
щитов, лазеров и фазеров адресуются отдельно). 36 = весь `DeviceCatalog`.

## Как обновлять

Файлы редактируются в игре («Tools → Buildings editor / Devices
editor»), сохраняются в пользовательскую папку, и оттуда копируются в
`~/.ascendancy/assets/common/...`, когда правку решено раздать всем.
Дальше обычный `tools/release.sh` — содержимое релиза берётся из
`~/.ascendancy/assets` как есть.
